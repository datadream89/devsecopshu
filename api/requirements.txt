ClaimTrack — Step 7: Proactive PreClear Assessment Detail and Human Review Action

Implement Step 7 only in the existing ClaimTrack repository.

Project context

Steps 1–6 have been implemented, with Step 6 subject to final manual validation.

- Step 1: Synthetic claims, assessments, events, and data dictionary.
- Step 2: FastAPI backend, SQLite, risk assessments, review tasks, and workflow APIs.
- Steps 3–5: Complete Shared Resolution experience across Provider, Member, and Claims Reviewer Portals.
- Step 6: Proactive PreClear internal dashboard showing first-pass, second-pass repeat-pend, and low-risk assessments.

Step 7 introduces a detailed assessment experience and a targeted Request Claims Review action.

The objective is to show how PreClear supports both first-pass pend prevention and repeat-pend prevention through explainable risk identification and human decision-making.

1. Inspect the repository first

Inspect the actual frontend routes, assessment schemas, synthetic data, API contracts, review-task models, authorization rules, and existing tests.

Reuse existing implementations.

Do not invent fields, risk factors, edit identifiers, or API contracts.

If a required field is absent, report the limitation. Only make the smallest compatible change when essential to Step 7, using synthetic data and documenting the change.

2. Create the Assessment Detail page

When an analyst selects a claim from the Step 6 dashboard, open a dedicated assessment detail page.

Display:

- Claim ID.
- Assessment type.
- Processing pass.
- Assessment timestamp.
- Illustrative risk category.
- Illustrative risk score, if available.
- Primary contributing factors.
- Existing claims-engine edit coverage.
- Recommended intervention.
- Review-task status, if applicable.

Use actual backend assessment data.

Clearly label risk estimates as illustrative, not validated model predictions.

3. Support first-pass and second-pass assessments

CLM-1001 — First-pass pend risk

Show that the assessment occurred before first-pass adjudication.

Explain the COB-related information risk using only the synthetic factors already available.

Recommend targeted review only when an actionable information gap is supported by the data.

Do not imply the claim previously pended.

CLM-1002 — Second-pass repeat-pend risk

Show that the claim previously pended, received processor action, and is being assessed before its next adjudication.

Explain the potential unresolved information issue using prediction-time information only.

Do not use the subsequent repeat-pend outcome as a model input or reason for the earlier assessment.

CLM-1003 — Low-risk control

Show the low-risk assessment and explain why no additional targeted PreClear intervention is recommended.

Do not imply that low risk guarantees payment.

4. Explain existing-edit coverage

Create a clearly labeled section:

Existing Claims-Engine Edit Coverage

Explain whether the identified information risk is:

- Already addressed by an existing edit.
- Partially addressed.
- Not demonstrably covered.
- Unknown because the prototype lacks sufficient information.

Only display coverage classifications supported by existing synthetic data.

Do not invent proprietary ProClaim edit codes, internal edit mappings, or enterprise integration details.

If coverage is unknown, display:

"Existing-edit coverage has not been established in this synthetic prototype."

Avoid recommending duplicate review when existing controls already adequately address the issue.

5. Recommended action

Create a section titled:

Recommended Next Action

Display a recommendation grounded in the available assessment factors and existing-edit coverage.

Possible outcomes include:

- Request targeted claims review.
- Continue normal processing.
- No additional PreClear intervention recommended.
- Insufficient evidence to recommend intervention.

Do not claim that a flagged pend is definitely preventable.

Do not introduce automatic claim holds or routing changes.

6. Implement Request Claims Review

Add a button labeled:

Request Claims Review

Use the existing review-task creation endpoint, expected to be:

"POST /api/claims/{claim_id}/review-tasks"

Inspect the actual API contract before implementation.

Use the existing internal demo role:

"X-Demo-Role: INTERNAL"

"X-Demo-Actor: analyst-001"

Submit only the fields required by the backend.

On success:

- Display the created review-task ID.
- Display task status.
- Display the associated claim ID.
- Show a confirmation message.
- Persist the task in SQLite.
- Refresh the task status on the assessment page.

The action creates an internal review request only.

It must not change adjudication status, automatically resolve COB information, or send an email.

7. Prevent duplicate review requests

Inspect existing review-task business rules.

If an active review task already exists for the same claim and assessment, avoid accidentally creating another identical active task.

Prefer existing backend duplicate protections.

If the backend does not enforce this rule, implement a minimal compatible safeguard with automated tests.

Handle duplicate requests gracefully and display the existing task when possible.

8. Keep the workflow human-in-the-loop

The assessment identifies risk and recommends an action.

An authorized claims reviewer remains responsible for investigating and deciding what, if anything, should happen next.

Do not automatically:

- Change claim disposition.
- Hold adjudication.
- Override an existing engine edit.
- Modify COB information.
- Approve payment.
- Mark a predicted pend as prevented.

9. Assessment explanation design

Use a clean, readable layout with these sections:

1. Claim and assessment overview.
2. Risk classification.
3. Contributing factors.
4. Existing-edit coverage.
5. Recommended next action.
6. Claims review task status.

Use deterministic explanations derived from existing synthetic assessment fields.

Do not call an LLM or implement model-generated explanations yet. That belongs to Step 8.

Avoid unsupported causal statements such as "This intervention will prevent the claim from pending."

10. Navigation

Ensure the user can:

- Open assessment details from the Step 6 dashboard.
- Return to the PreClear worklist.
- Refresh the assessment and task status.
- Navigate between different assessments.

Preserve all existing Shared Resolution portal functionality.

11. Error handling

Handle:

- Missing claim.
- Missing assessment.
- Unauthorized access.
- API unavailable.
- Invalid review-task request.
- Duplicate review request.
- Concurrent task creation.
- Failed persistence.
- Stale frontend state.

Do not fabricate successful responses when the backend fails.
