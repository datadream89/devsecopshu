ClaimTrack — Step 5: Claims Reviewer Verification and Shared Resolution Integration

Implement Step 5 only in the existing ClaimTrack repository.

Project context

The following steps have been implemented:

- Step 1: Synthetic claims, assessments, events, and validation.
- Step 2: FastAPI backend, SQLite persistence, workflow state machine, demo roles, and APIs.
- Step 3: React Provider Portal displaying CLM-2001's pending COB status and provider-visible timeline.
- Step 4: React Member Portal allowing COB information submission.

The objective of Step 5 is to complete the end-to-end workflow:

Member submits COB information → Claims reviewer verifies it → Provider sees a verified resolution milestone.

1. Inspect the existing implementation

Before coding, inspect the repository, backend endpoints, Pydantic schemas, React components, state transitions, authorization logic, and tests.

Reuse existing API contracts and backend services. Do not duplicate workflow logic or introduce incompatible fields.

2. Build the Claims Reviewer Portal

Create a professional, responsive React page for the "CLAIMS_REVIEWER" role.

Display:

- Claim number: "CLM-2001"
- Current COB workflow status
- Member submission status and timestamp
- Submitted COB information, limited to fields authorized for reviewer access
- A clearly labeled Verify COB Information action
- Reviewer action confirmation and error messages

The reviewer must be able to verify a submission only after the member has submitted the required information.

Do not automatically verify information when the page loads.

3. Integrate with the existing FastAPI backend

Use the existing verification endpoint:

"POST /api/claims/CLM-2001/verify-cob"

With demo headers:

"X-Demo-Role: CLAIMS_REVIEWER"

"X-Demo-Actor: reviewer-001"

Use the actual request and response schemas already implemented.

Expected successful state transition:

"AWAITING_COB_VERIFICATION"

↓

"COB_VERIFIED_AWAITING_CLAIMS_REVIEW"

The backend must persist the reviewer action, actor, and timestamp.

Do not automatically approve, adjudicate, or pay the claim.

4. Integrate the Provider Portal

After reviewer verification, refreshing the existing Provider Portal must display the updated status and a verified timeline milestone.

Use this provider-safe message:

"Member COB verification completed. Next: Claims review."

The provider must not see private member insurance identifiers, raw COB submission payloads, or internal-only reviewer notes.

The timeline must be generated from backend events, not hardcoded frontend milestones.

5. Integrate the Member Portal

After verification, refreshing the Member Portal should display:

"Your COB information has been verified. Your claim is awaiting further review."

Do not imply the claim has been approved or payment is guaranteed.

Ensure the member cannot resubmit COB information once the workflow no longer permits it.

6. Demo navigation

Provide simple navigation among:

- Provider Portal
- Member Portal
- Claims Reviewer Portal

Use clearly labeled simulated roles.

Navigation must not reset the claim state.

The existing backend remains the source of truth for all status changes.

7. Error handling and safeguards

Handle the following scenarios:

- Verification attempted before member submission
- Duplicate verification
- Unauthorized verification attempts
- Missing claim
- Network or API failure
- Stale frontend state
- Invalid workflow transitions

Use the existing HTTP status conventions, including HTTP 409 where appropriate.

Do not bypass backend authorization or workflow validation.

8. Automated tests

Add tests verifying:

1. Verification before member submission is rejected.
2. Member submission transitions the claim to "AWAITING_COB_VERIFICATION".
3. An authorized claims reviewer can verify the submission.
4. Unauthorized roles cannot verify.
5. Duplicate verification is rejected appropriately.
6. Verification persists in SQLite.
7. The Provider Portal displays the verified milestone after refresh.
8. The Provider Portal does not expose private member data.
9. The Member Portal displays the updated status.
10. Existing Steps 1–4 tests continue to pass.

9. Design requirements

Maintain the same design system as the existing Member and Provider Portals.

Use clean enterprise styling, accessible controls, clear status indicators, and a chronological resolution timeline.

Make the experience presentation-ready for the Aspire iTournament finals.

Use synthetic information only.

- Proactive PreClear Dashboard (Step 6)
- PreClear assessment detail (Step 7)
- ML or GenAI explanations (Step 8)
- Email notification delivery or previews (Step 9)
- Automatic adjudication or claim payment
- Real authentication or production integration
