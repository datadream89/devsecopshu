ClaimTrack — Step 6: Proactive PreClear Dashboard

Implement Step 6 only: Proactive PreClear Internal Dashboard in the existing ClaimTrack repository.

Project context

Steps 1–5 are implemented and validated:

- Step 1: Synthetic claims, assessments, events, and data dictionary.
- Step 2: FastAPI backend, SQLite persistence, assessment APIs, review-task APIs, workflow rules, and demo roles.
- Step 3: React Provider Portal.
- Step 4: React Member Portal.
- Step 5: Claims Reviewer Portal and end-to-end Shared Resolution integration.

Step 6 introduces the second major ClaimTrack capability: Proactive PreClear.

The goal is to demonstrate how claims can be assessed for information-related pend risk before their relevant adjudication pass.

This is an internal claims-processing capability, separate from the member/provider Shared Resolution experience.

1. Inspect the existing repository

Before implementing anything, inspect:

- Existing React frontend structure and navigation.
- FastAPI assessment endpoints and response schemas.
- Synthetic claims and risk assessments.
- Review-task endpoints.
- Event timestamps and processing-cycle metadata.
- Existing authorization rules and tests.

Reuse the existing backend contracts and data.

Do not invent incompatible fields or change validated business logic.

2. Build the PreClear Dashboard

Create a new React page:

Proactive PreClear — Claims Risk Worklist

Use the existing design system and navigation.

The dashboard should show:

- Total assessed claims.
- High-risk claims.
- Low-risk claims.
- First-pass risk assessments.
- Second-pass repeat-pend risk assessments.

These counts must be derived from backend assessment records, not hardcoded.

Clearly label the dashboard as a synthetic prototype.

3. Display the assessment worklist

Retrieve assessments from the existing FastAPI backend.

Use the appropriate internal demo role, following actual backend authorization rules.

Expected demo identity:

"X-Demo-Role: INTERNAL"

"X-Demo-Actor: analyst-001"

Display a table with:

- Claim number.
- Assessment type.
- Processing cycle.
- Risk category.
- Illustrative risk score, if available.
- Primary risk driver.
- Recommended action.
- Assessment timestamp.
- Action to view assessment details.

Use actual backend field names and values.

Do not fabricate assessment scores or explanations.

4. Demonstrate the three synthetic claims

CLM-1001 — First-pass risk

Display:

- First-pass assessment.
- High illustrative risk.
- COB-related information risk.
- Recommendation for targeted review before first-pass adjudication.

This claim must not be presented as having previously pended.

CLM-1002 — Second-pass repeat-pend risk

Display:

- Second-pass assessment.
- High illustrative repeat-pend risk.
- Evidence of a previous pend and subsequent reprocessing.
- Recommendation for review before second-pass adjudication.

Do not confuse first-pass and repeat-pend predictions.

CLM-1003 — Low-risk control

Display:

- First-pass assessment.
- Low illustrative risk.
- No targeted intervention recommended.

Do not imply that low risk guarantees successful adjudication.

5. Dashboard filters

Provide simple frontend filters:

- All assessments.
- First-pass.
- Second-pass.
- High risk.
- Low risk.

Allow sorting by risk score or assessment timestamp if supported by the available data.

Keep filtering simple and fast.

Do not introduce unnecessary backend endpoints.

6. Assessment chronology and data integrity

Preserve the distinction between prediction-time information and historical outcomes.

For CLM-1001 and CLM-1003, assessments must precede first-pass adjudication outcomes.

For CLM-1002, the assessment must occur after the first pend and processor action but before the second-pass adjudication outcome.

Never use final disposition, subsequent pend outcome, or other future information as prediction features.

If historical outcomes are displayed anywhere, label them clearly as subsequent observed outcomes, not prediction inputs.

7. Dashboard interactions

Include:

- Refresh Assessments button.
- Loading state.
- Empty state.
- API error handling.
- Unauthorized-access handling.
- Clickable claim rows or a View Assessment action.

For Step 6, clicking an assessment may open a simple read-only summary using the existing API data.

Do not build the complete assessment detail experience yet; that belongs to Step 7.

8. Visual design

Use a polished, professional internal enterprise dashboard.

Prioritize readability and clear risk differentiation.

High-risk claims should be visually prominent without excessive red styling.

Low-risk claims should be visibly distinct.

Use appropriate labels:

- First-Pass Pend Risk
- Second-Pass Repeat-Pend Risk
- High Risk
- Low Risk
- Recommended Review
- No Targeted Intervention

Avoid claiming that the system prevents pends automatically.

Include a small disclaimer:

"Risk assessments are illustrative and based on synthetic data. Predictive performance has not been validated."

9. Navigation

Add Proactive PreClear to the existing application navigation.

Preserve the existing:

- Provider Portal.
- Member Portal.
- Claims Reviewer Portal.

Keep internal and external portal experiences clearly differentiated.

Do not modify the Shared Resolution workflow.
