ClaimTrack — Step 9: Event-Driven Notifications & Simulated Email Outreach

Implement Step 9 only in the existing ClaimTrack repository.

Project context

ClaimTrack is a synthetic claims-processing prototype for the Cigna Aspire iTournament 2026 finals.

The application has two capabilities:

Proactive PreClear

- Identifies potential information-related pend risks before first-pass or subsequent-pass adjudication.
- Provides ML-assisted risk assessments and explanations.
- Allows internal analysts to request targeted claims review.

Shared Resolution

- Displays pending COB claims in the Provider Portal.
- Allows members to submit COB information.
- Allows authorized claims reviewers to verify submitted information.
- Publishes provider-visible verified milestones.

Steps 1–8 have been implemented. Step 8.5 (detailed Model Transparency) has been intentionally skipped.

Step 9 adds an event-driven notification simulation to both workflows.

The objective is to demonstrate how ClaimTrack could support timely outreach without implementing real email delivery.

All notifications must be synthetic, privacy-safe, and explicitly labeled as simulations.

2. Implement a lightweight notification service

Create a backend notification service responsible for generating simulated notification records from eligible workflow events.

Notifications must be triggered by actual persisted workflow events, not by frontend page loads.

Each notification should include:

- Notification ID.
- Related claim ID.
- Triggering workflow event ID or equivalent reference.
- Event type.
- Recipient role.
- Synthetic recipient reference.
- Notification channel: EMAIL_PREVIEW.
- Template identifier.
- Email subject.
- Email body.
- Creation timestamp.
- Simulation status: PREVIEW_ONLY_NOT_SENT.

Use SQLite persistence.

Reuse existing event IDs where available.

Do not create fake delivery timestamps, SMTP message IDs, or delivery confirmations.

A notification record represents a simulated email that would be generated, not an email that was actually sent.

3. Implement Shared Resolution notification triggers

Support the following notification scenarios.

A. COB information required

Trigger when CLM-2001 enters the existing pending-member-COB state.

Recipient: MEMBER.

Subject:

"Action required: Update your COB information"

Body:

"Additional information is needed to continue reviewing your claim. Please sign in to your secure member portal to provide the requested information."

Important:

CLM-2001 may already be in the pending state when Step 9 is installed.

Do not manufacture a new state transition simply to generate a notification.

For demonstration purposes, allow a clearly labeled, idempotent initialization or backfill of the notification associated with the existing synthetic pending event.

Do not generate a new notification every time the page loads.

B. Member COB submission received

Trigger when the member successfully submits COB information.

Recipient: MEMBER.

Subject:

"We received your COB information"

Body:

"Your coordination of benefits information has been received and is awaiting verification. We will update your claim status as the review progresses."

Do not imply that submission means verification has been completed.

C. COB verification completed

Trigger after an authorized claims reviewer successfully verifies the submitted information.

Recipient: MEMBER.

Subject:

"Your COB information has been verified"

Body:

"Your coordination of benefits information has been verified. Your claim is awaiting further claims review."

Do not promise claim approval or payment.

D. Provider status milestone available

Trigger when the verified COB milestone becomes provider-visible.

Recipient: PROVIDER.

Subject:

"Claim status update available"

Body:

"A verified coordination of benefits update is available. Please sign in to your provider portal to review the latest claim status."

Do not include raw member insurance information in the email.

Do not imply the claim has been paid.

4. Implement Proactive PreClear notification trigger

When an internal analyst successfully creates a Request Claims Review task for CLM-1001 or CLM-1002, generate a simulated internal review notification.

Recipient: INTERNAL_CLAIMS_REVIEWER or the existing equivalent authorized role.

Subject:

"New claim review task available"

Body:

"A claim has been identified for targeted information-related review. Please sign in to the internal ClaimTrack worklist to review the assessment and assigned task."

Associate the notification with the actual review-task creation event and task ID.

Do not generate a notification merely because a risk assessment was viewed.

Do not automatically create a review task.

Do not alter claim adjudication status.

For existing review tasks created before Step 9, use an explicitly documented, idempotent demo backfill only if needed.

---

5. Implement duplicate-notification protection

A workflow event must not generate duplicate notifications for the same recipient, channel, and template.

Use a durable database uniqueness constraint or equivalent transactional protection.

Ensure:

- Browser refresh does not generate notifications.
- React navigation does not generate notifications.
- Retrying a successful request does not generate duplicate notifications.
- Concurrent processing of the same event does not create duplicates.
- A legitimate new workflow event may generate a new notification.

Do not rely exclusively on frontend duplicate prevention.

---

6. Preserve workflow transaction integrity

Notifications must reflect successful persisted workflow events.

Do not create a notification when the underlying business action fails.

Prefer creating the notification in the same database transaction as the relevant workflow event when compatible with the existing architecture.

Otherwise, use a documented, idempotent event-processing approach that can recover from partial failures.

A notification failure must not silently corrupt claim state.

Do not make outbound network calls.

10. Authorization and privacy

Follow the existing demo-role conventions.

Expected roles include:

- MEMBER.
- PROVIDER.
- CLAIMS_REVIEWER.
- INTERNAL.

Inspect actual backend authorization rules.

The internal Notifications page may provide a synthetic administrative overview, but it must be restricted to an appropriate internal role.

Member and provider users must not access the complete internal notification history.

Enforce notification visibility at the backend, not only through React filters.

Ensure provider-facing messages contain no raw member COB submissions or insurance identifiers.

Remember that demo headers simulate roles and do not constitute production authentication.

Do not introduce real PHI.
