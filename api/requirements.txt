ClaimTrack — Step 8: Illustrative ML Risk Assessment and Grounded GenAI Explanations

Implement Step 8 only in the existing ClaimTrack repository.

Project context

Steps 1–7 have been implemented:

- Step 1: Synthetic claims, assessments, and event histories.
- Step 2: FastAPI backend, SQLite, and workflow APIs.
- Steps 3–5: Shared Resolution portals and reviewer verification.
- Step 6: Proactive PreClear Dashboard.
- Step 7: PreClear Assessment Detail and Request Claims Review.

Step 8 introduces an illustrative machine-learning risk assessment and a grounded natural-language explanation capability.

The objective is to demonstrate a technically credible AI-assisted approach without presenting synthetic results as validated production predictions.

Preserve the existing application architecture and functionality.

1. Inspect the repository first

Before making changes, inspect:

- Existing synthetic claims and assessments.
- Data dictionary and event timestamps.
- FastAPI assessment schemas and endpoints.
- React PreClear Dashboard and Assessment Detail components.
- Existing risk factors and recommendations.
- Review-task functionality.
- Existing Python dependencies and tests.

Reuse existing components and API contracts wherever possible.

Do not silently overwrite or invalidate previously validated assessment data.

2. Create a separate synthetic ML training dataset

The three existing PreClear demonstration claims are insufficient for meaningful model training.

Create a reproducible synthetic dataset specifically for demonstrating the ML pipeline.

Requirements:

- Use synthetic data only.
- Use a fixed random seed.
- Document the synthetic data-generation assumptions.
- Include a reasonable number of illustrative records, such as 1,000–3,000.
- Include both first-pass and subsequent-pass processing scenarios.
- Include examples of information-related pends and claims that do not pend.
- Include relevant COB-related and information-completeness indicators only where supported by the synthetic data dictionary or explicitly documented as newly simulated features.

Every feature must be available before the relevant adjudication decision.

Never include:

- Final claim disposition as an input.
- Future pend outcomes as an input.
- Future reviewer actions.
- Post-adjudication information.
- Identifiers that leak the target label.
- Real PHI or proprietary claims data.

Historical outcomes may be used as training labels, but not as prediction features for the same decision.

For second-pass assessments, prior-pass history may be used only if it existed before the second-pass assessment.

Do not train on CLM-1001, CLM-1002, or CLM-1003. Reserve them as illustrative demo cases.

3. Implement a simple reproducible ML pipeline

Use scikit-learn if compatible with the existing environment.

Prefer an interpretable baseline model such as logistic regression.

Use appropriate preprocessing for categorical and numerical features.

Implement:

- Synthetic dataset generation.
- Feature selection and preprocessing.
- Train/test split.
- Model training.
- Evaluation.
- Model artifact persistence.
- Inference.

Use a fixed random seed and reproducible configuration.

Ensure the same model artifact and input produce consistent predictions.

Keep model training separate from normal FastAPI request handling.

Do not retrain the model whenever a user opens an assessment page.

4. Handle first-pass and repeat-pend risk correctly

Support two clearly defined prediction contexts:

First-pass information-pend risk

Estimate the illustrative probability of an information-related pend at first-pass adjudication.

Subsequent-pass repeat-pend risk

Estimate the illustrative probability of another information-related pend at the upcoming adjudication pass, using only information available at that point.

These may be handled using separate models or a shared model with explicit processing-pass features, provided the distinction is documented and tested.

Do not mix historical outcomes into the prediction features.

5. Evaluate the model transparently

Report:

- Training and test record counts.
- Class distribution.
- ROC-AUC when mathematically defined.
- Precision.
- Recall.
- Confusion matrix.
- Any important limitations.

Use a held-out synthetic test set.

If practical, include a simple calibration check.

Clearly state:

"Model performance is measured on synthetic data and does not establish real-world predictive accuracy."

Do not invent evaluation metrics or present them as production results.

6. Integrate ML inference with PreClear

Implement a backend inference service that accepts valid prediction-time features and returns:

- Claim ID or assessment reference.
- Assessment type.
- Processing pass.
- Illustrative risk score.
- Risk category.
- Model version.
- Assessment timestamp.
- Input feature provenance or a traceable reference to the input snapshot.

Inspect the existing API contracts and choose the smallest compatible integration.

Prefer a read-only inference endpoint or a clearly controlled assessment-generation action.

Do not change existing claim adjudication states.

Do not overwrite historical assessment snapshots without an explicit versioning strategy.

Keep existing CLM-1001, CLM-1002, and CLM-1003 dashboard behavior intact.

If the newly trained model produces scores or risk categories that differ from the original illustrative assessment records, do not secretly alter scores, force labels, or cherry-pick outputs to make the demo appear successful.

Instead, distinguish:

- Existing synthetic assessment snapshot.
- New illustrative ML model output.

Document discrepancies transparently.

7. Implement grounded GenAI explanations

Create a structured explanation layer that takes:

- Model output.
- Available prediction-time features.
- Assessment type.
- Supported contributing factors.
- Existing-edit coverage information.
- Recommended review action, when supported.

Generate concise, understandable explanations for claims analysts.

The explanation should answer:

1. What risk is being assessed?
2. Which available factors support the assessment?
3. What information may require attention?
4. What is known about existing claims-engine edit coverage?
5. What action, if any, is recommended?

Important requirements:

- Never invent missing COB information.
- Never invent existing claims-engine edits.
- Never claim a pend will definitely occur.
- Never claim a pend is definitely preventable.
- Never claim a claim will be paid.
- Never describe correlation as proven causation.
- Never imply the model has been validated on real claims.
- Do not expose private member insurance information.

Do not simply label a generic template as an actual LLM-generated explanation.

Implement a provider-neutral explanation interface.

If an approved LLM provider and credentials are already configured, an optional LLM-backed implementation may be used.

Do not introduce external AI services, send data to a third party, or require new API keys without explicit approval.

Provide a deterministic, grounded explanation fallback that works entirely offline.

Clearly identify in the UI whether an explanation was generated by an LLM or by deterministic rules.

8. Ground explanations in actual model evidence

Do not assume that a field is a contributing risk factor merely because it appears in the input.

Use an appropriate interpretable method, such as logistic-regression contributions or another documented explanation method, to identify relevant model-supported factors.

Clearly distinguish:

- Model-supported factors.
- Observed claim information.
- Business-rule recommendations.
- Unknown information.

If model contributions are unavailable or unreliable, do not fabricate feature importance.

Keep explanations consistent with the actual risk score and feature snapshot.

11. Preserve the human-in-the-loop architecture

The ML model provides risk intelligence.

The explanation layer supports analyst understanding.

The analyst decides whether to request targeted claims review.

The existing claims engine remains responsible for adjudication.

Do not automatically:

- Pend a claim.
- Prevent a pend.
- Hold adjudication.
- Change claim disposition.
- Modify COB records.
- Approve or deny payment.
- Send notifications.
